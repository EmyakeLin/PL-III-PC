# 《光点三》（PL-III）阶段性架构设计与代码实现总结

**文档路径**: `AI chat/阶段性开发总结与核心架构梳理.md`  
**记录时间**: 2026年10月  
**核心体系**: 纯栈式虚拟机（Forth / Hex Casting 范式） + 动态展开双轨管线系统  

---

## 一、 项目背景与核心范式

《光点三》（PL-III）是一款卡牌与骰子驱动的非对称战术对抗游戏。在系统底层，游戏摒弃了传统卡牌游戏硬编码“造成 X 点伤害”的面向对象死逻辑，全面引入了借鉴自 Minecraft 模组 **Hex Casting** 的核心范式：
1. **代码即数据（Code as Data）**：一切技能、伤害、状态、置卡、抽卡，在底层全部表现为由**操作数（Operands）**与**操作子（OpCodes）**构成的逆波兰指令流（RPN）；
2. **纯栈式求值机（Evaluation Stack）**：虚拟机（`Context`）拥有统一的数据栈（`stack`）与寄存器（`register`），计算与执行完全依靠出栈（`pop`）与压栈（`push`）；
3. **时钟时序表（PipelineNodeTraceTable）**：将回合生命周期完全拆解为高精度时间轴，能发 Trigger 的节点遍布全场，词条依靠自身生命周期作用域自然捕获时钟。

## 二、 核心架构技术突破与设计思路

在开发过程中，系统完成了四大核心架构的跃迁：

### 1. 动态指令流与纯栈操作码审查（消灭标志位硬编码）
* **旧痛点**：原本 `eval_block` 采用静态 `for item in block` 循环，导致一旦指令在执行中途被拦截（例如“不抽卡转为伤害”、“即将被摧毁时免死”），只能依靠在 Context 挂载丑陋脆弱的布尔标志位（如 `is_intercepted`）。
* **新架构**：
  - **指令流传送带（`self.code_stream = deque(block)`）**：指令被解放为动态双端队列，词条可在执行时随意清空流水线（`clear`）或队头插队新指令（`extendleft`）；
  - **操作码调用栈（`self.op_stack`）**：当前正在执行的操作码置于栈顶（`self.current_op`）。遇到反制拦截时，词条直接调用纯栈方法 `ctx.cancel_op()`（即 `op_stack[-1] = None`），当前操作码原地抹杀灰飞烟灭，零脏状态污染。

### 2. 依赖注入与图谱关系约束求解器（`@expect` 契约体系）
* **旧痛点**：字符串简写词条在翻译为指令流时，如果写死 `owner.player`，面对“场地效果”、“自身就是 Player”、“多阵营混战”等情况会当场报错，属于典型的硬编码思维。
* **新架构**：
  - **函数自治契约**：每个 `stack_xxx` 通过 `@expect(args=[...], rules=lambda ...)` 自主向外宣告自己需要几个文本参数、以及期待什么样的实体；
  - **零硬编码对象图谱遍历（`collect_universe`）**：利用 Python 原生反射 `__dict__` 动态向上沿引用网络广度优先搜索（BFS），全篇不写任何一个特定属性名，彻底消灭属性散弹枪；
  - **关系约束求解器（`solve_constraints`）**：在候选全集中通过排列组合代入 `rules` 逻辑，不仅能求单个实体，还能完美求解网状复杂关系（如 `source == owner and target not in all_allies`）。

### 3. 动态展开管线与 PackType 偏序调度（消灭静态循环节）
* **旧痛点**：两边卡牌数量不对称（A 方 1 张卡 1 颗骰子，打完要换卡；B 方 1 张卡 3 颗骰子，还在卡 1 内部）；单方面攻击时对方无卡。用传统单轨大循环（`PipelineSection`）在数学上必然死锁，强行同步或异步都会导致“A 还在打命中，B 提前结算使用后”的时序灾难。
* **新架构**：
  - **三线协同**：1 条中立主管线 `Pipeline` 负责裁判；2（或多）条阵营私有管线 `SidePipeline` 负责各跑各的卡牌进出；
  - **以 Pack 为单元动态展开（Push Pack）**：彻底拔除静态循环节，主管线根据战局事实，向被阻塞的 `SidePipeline` 队头注入自包含的微观结构包（`Packed DUEL / SKILL / DICE / CLASH / HIT`）；
  - **PackType 偏序阶梯收敛（低等高，谁都不等 None）**：
    $$\text{DUEL} > \text{SKILL} > \text{DICE} > \text{CLASH} > \text{HIT} > \text{NONE}$$
    - `CLASH` 严格等待 `HIT` 打完，败方在原地等待赢家命中全部结束，双方在 `after_clash` 和 `after_dice_use` **绝对同生共死同时收尾**！
    - `DICE` 严格等待 `SKILL` 换卡并产出新骰子，双方在下一颗骰子的起手点自然重新咬合；
    - 任何人都不用等 `NONE`，单方面攻击与中途阵亡瞬间自愈放行！
  - **最近匹配原则**：所有 `wait_xxx_check` 节点作为一等公民触发器无差别广播时钟，各方在自己的轨道上奔跑，直到撞上最近的同类检查点自然对齐。

### 4. 正交多维伤害与双重防御矩阵
* **维度一：穿透等级（`penetration`）**：`normal` 普通 / `pierce` 穿甲 / `concept` 超穿甲，严格对接普通护盾、强化护盾、概念护盾的穿透与抵御矩阵；
* **维度二：攻击物理形态（`attack_type`）**：`slash` 斩击 / `pierce` 突刺 / `blunt` 砸击 / `none` 无形态效果伤害，缺省时自动继承当前进攻骰子自身类型；
* **受击角色三路径判定**：
  1. 拼点对撞 $\to$ 对撞骰子所属角色；
  2. 无拼点前线有卡 $\to$ `current_opposing_card` 所属角色（随换卡动态转移）；
  3. 槽位完全无卡 $\to$ 交互询问玩家，回车使用玩家个人可随时修改的默认目标！

## 三、 完成工作清单与文件代码归属

## 四、 全流程端到端实测验证总结

经 Python 自动化端到端测试，系统完整验证了以下全链路：

```text
1. 启动选人：加载 2 个精英角色，完成卡组装配，Draw 堆各自拥有独立 5 张卡牌并完成洗牌。
2. 回合开始：投掷速度骰决出先手 -> 双方抽取并选弃卡牌 -> 费用重置为基础 5 点 + 独立 1 点。
3. 置卡阶段：手牌扣除 -> 纯栈指令 Place-Card 展开 -> 在槽位 0 扣置落位 (PLACED_FACE_DOWN)。
4. 开牌阶段：翻转为明置 (PLACED_FACE_UP) -> 触发 logic_start_duel_combat 启动双方 SidePipeline。
5. 对决推进：
   - 双方摸出骰子 -> wait_can_clash_check 全员广播并就位 -> ClashPair 组装并下发 CLASH 包；
   - 双方流经 logic_dice_clash 真实投掷算点 -> 比对出胜负 -> 输家拿 LOSE 包，赢家拿 WIN 包；
   - 赢家被 wait_can_hit_check 拦截注入 HIT 包，输家位阶为 CLASH 原地冻结等待；
   - 赢家跑完 before_dice_hit -> logic_dice_hit 执行伤害，扣除输家真实 HP；
   - 赢家 HIT 结束回落为 CLASH，双方同时迈入 after_clash 与 after_dice_use 完美收尾！
6. 轮次间隙：卡牌打完的一方独立退出触发 after_skill_use 换新卡，未打完的一方停在原卡等待下一轮！
7. 终局收尾：致死伤害触发角色即时阵亡并熔断战局，宣告胜者平稳退出。
```

全工程 15 个源文件编译 **零语法错误、零类型警告**，系统随时可继续深入延展拼点与复杂词条机制！
